## 一、问题与证据

### 1.1 真实问题

大语言模型正在成为科学研究中的常用工具，但它本质上是一个概率黑盒。当我让一个本地部署的 Qwen2.5-7B 模型做物理计算时，它把加速度 `9.8 m/s²` 当成了速度 `9.8 m/s`——一个量纲逻辑错误。这个答案表述流畅、看起来合理，但物理量的性质被混淆了。人类读者如果不去逐行核验单位，很难发现这个错误。

这不是孤例。在开发过程中，我反复观察到四类逻辑错误：第一类是量纲错误，模型混淆了加速度与速度、能量与力等物理量的基本性质；第二类是符号错误，模型在展开 `(x+1)²` 时写成了 `(x-1)²`，一个负号之差；第三类是等价性错误，模型声称 `x²+2x+2` 等于 `(x+1)²` 的展开，多了一个常数项；第四类是证明占位符，模型在 Lean 形式化证明中使用 `sorry` 或 `admit` 来冒充一个证明步骤。这些错误的共同特征是：它们不是事实性幻觉（模型没有编造一个不存在的知识），而是推理步骤本身在逻辑上无效。

更令人担忧的是，现有的大多数系统只有"对"和"错"两种状态。当一个推理步骤无法被判定时，系统默认它"没有问题"——这就是我所说的"静默放行"（silent pass）。一个逻辑上无效的步骤就这样混过了验证，被当作通过了。

### 1.2 为什么尚未被结构化

这个问题的核心困难在于，"推理是否有效"不像"答案是否正确"那样有单一判据。一个逻辑错误可能发生在量纲、符号、定义域、形式化等任何一个层面，没有统一的检查框架。现有的方法各有局限。

最直觉的做法是让模型自我修正——让同一个 LLM 检查自己的推理。但自我修正对格式和风格问题有效，对逻辑正确性却效果甚微，甚至为负。原因很简单：模型对错误步骤的置信度往往很高——这正是它犯错的原因。让一个概率黑盒去判断同一个概率黑盒的推理是否正确，等于用不可靠性去检查不可靠性。

另一种做法是用一个独立的 LLM 作为逻辑判官。这比自我修正好一些（至少实现了关注点分离），但仍然是概率判断概率，无法给出确定性的裁决。一旦判官本身犯了逻辑错误——而它作为一个概率模型必然会犯——整个验证链就断裂了。

可解释性研究（激活向量、转向向量、电路分析）能帮助定位错误，但它们本身不产生确定性判定。它们告诉你"这一层的激活模式异常"，但不能告诉你"这个推理步骤在逻辑上是否有效"。

此外，本地 LLM 和云端 LLM 在这个问题上面临不同的约束。本地模型可以输出完整的推理链（chain-of-thought），允许做步骤级别的验证；云端模型通常只返回最终答案，中间步骤不可见，只能做输出级别的验证。这两种情况的验证粒度不同，但都需要一个诚实的框架来处理"我看不到中间步骤"这种情况——而不是假装它不存在。

### 1.3 研究价值与合适切片

我不会声称要"修复 LLM 的推理能力"——那是一个终极问题，远超比赛周期。我切片后的研究问题是：

> 一个确定性验证器能捕获 LLM 科学推理中逻辑错误的比例是多少？这个覆盖边界在哪里？它能否被人类审批的验证器规则扩展安全地推进？

这个切片的价值在于：它不要求修复概率黑盒，而是为黑盒的输出构建一个确定性的安全网。AI 在这里的独特角色不是"判定正确性"（这是确定性验证器的工作），而是"提议新的检查规则"。当验证器遇到一个它无法判定的推理步骤时（即"弃权"），LLM 可以提议一个新的检查器——例如"检查碰撞前后动量是否守恒"。这个提议经过人类所有者审批和独立专家 AI 审查后，成为一个新的确定性规则，覆盖范围就安全地扩大了一格。

这就是"识别逻辑错误并引导方向"：LLM 擅长生成（提议新规则），不擅长评估（判定正确性）；把它的优势用在提议上，把判定交给确定性检查。

## 二、环境接口

### 2.1 固定规则

这个探索环境有几条不可改变的规则。第一，三态判定是唯一允许的输出：accepted（一个可执行检查确立了候选）、rejected（一个可执行检查反驳了候选）、abstain（没有可执行检查能判定，诚实弃权）。第二，弃权永远不等于通过——它是诚实的"我还验证不了"，不是静默放行。第三，基础验证器在评分前冻结：SI 量纲检查、SymPy 符号等价、Lean 内核检查，它们的规则在探索开始前就已固定。第四，开放问题（如尚未形式化的数学难题）永远不能被晋升为 accepted——它们没有可执行规约，任何尝试"解决"它们的提议都必须被拒绝。第五，模型永远不能自我批准其提议的检查器——批准需要人类所有者和独立专家 AI 的双重审批。

### 2.2 观察、行动与反馈

Agent 在这个环境中能看到的信息是一个候选答案或推理步骤。对于本地 LLM，这包括完整的推理链；对于云端 LLM，只有最终答案。

Agent 可以执行两种动作。第一种是将候选判定为 accepted、rejected 或 abstain。第二种是在 abstain 之后，提议一个新的有界检查器——一个规约或验证器规则，用于覆盖之前无法判定的步骤类别。

每个动作之后，Agent 收到的反馈来自确定性验证器：它立即返回一个裁决（accepted/rejected/abstain）和一个原因码（如 `dimension_mismatch`、`not_equivalent`、`proof_placeholder`）。这个反馈是完全确定性的——没有学习型判官参与，没有网络调用，完全可复现。如果候选被 rejected，Agent 允许进行一次有界修正（revise-once），然后重新提交验证。

### 2.3 记录与预算

探索过程中的每一个判定和每一个提议的扩展都被记录为一个内容寻址的 receipt——规范 JSON 的 SHA-256 哈希。这些 receipt 形成一个证据有向无环图（DAG）：提案→所有者审批→专家审查→可执行测试→激活→迁移→受保护套件→回滚→扩展链。这个 DAG 就是实验日志本身——它不可篡改，任何链接断裂、交叉链接或自我声明都会导致结果无效。

每个任务家族的资源预算是固定的：120 秒执行时间、2048 MiB 内存、最多 10 个测试、无网络访问、无凭证访问、仅使用临时 scratch 空间。所有失败都被保留——从不丢弃或重试以隐藏一个失败的结果。

## 三、发现信号与参照

### 3.1 什么算发现

我在探索开始前预注册了四种发现信号。

第一种是正向发现：一个被人类批准的新检查器成功地将一个之前弃权的推理步骤移入了 accepted 或 rejected——覆盖边界推进了一格。第二种是异常：验证器捕获了一个人类未预期的错误模式，例如一个新的量纲陷阱类别，或者一个在特定条件下才出现的符号错误。第三种是稳定负结果：一个开放问题在所有尝试后仍然 abstain——这证明覆盖边界是真实的，不是工具不足，而是问题本身尚未被结构化。第四种是失败模式：模型试图走私答案或自我批准其提议，被策略门捕获——这些失败作为完整性证据保留，而不是被隐藏。

### 3.2 平凡解、随机与无干预

我设计了三个参照系来比较。第一个是原始模型（无验证器）：模型直接输出答案，不经过任何检查——它的逻辑错误率是基线。第二个是 always-abstain：对一切候选都弃权——覆盖率是 0%，但不安全接受也是 0%。第三个是 always-accept：对一切候选都通过——覆盖率是 100%，但不安全接受率很高。

我的系统必须同时优于这三个参照：比原始模型有更低的逻辑错误率，比 always-abstain 有更高的覆盖率，比 always-accept 有更少的不安全接受。只有同时满足这三个条件，才能认为探索结果超过了参照。

### 3.3 最低成功与失败标准

最低成功门槛是：在已知逻辑错误探测项上零不安全接受（任何一个被接受的候选实际包含逻辑错误即为失败），同时在 frontier-gap 项上实现非零覆盖扩展（至少一个之前弃权的步骤被人类批准的新检查器解决）。

明确的失败判定是：任何一个 accepted 落在开放控制项（无形式化规约的任务）上——这意味着覆盖边界被突破，一个不应被判定的问题被错误地接受了。或者验证器漏判了一个已植入的逻辑错误——这意味着该层验证器有缺陷，需要修复。

当失败发生时，我会缩小验证器的覆盖范围（更保守地弃权）；当成功时，我会尝试扩展到更难的问题类别。

## 四、最小验证计划

### 4.1 一次试跑怎么做

这次试跑的目标是测量确定性验证器对已知逻辑错误的捕获率。

我构造了 16 个带有已知逻辑错误的候选项：8 个 SI 量纲错误（如把 `m/s²` 当成 `m/s`、把 `J` 当成 `m/s`）、6 个 SymPy 等价性错误（如把 `x²+2x+2` 当成 `(x+1)²`、把 `(x-1)²` 当成 `(x+1)²`）、以及 2 个 Lean 证明占位符（`sorry` 和 `admit`）。每个候选项都配有正确的参考答案。

试跑的步骤是：对每个候选项运行对应的确定性验证器（SI 量纲检查器、SymPy 等价检查器、Lean 占位符拒绝器），记录每个的裁决和原因码，然后统计捕获率。

试跑的结果是：16 个已植入的逻辑错误全部被确定性验证器捕获，捕获率 100%，零漏判。其中 SI 层捕获了全部 8 个量纲错误，SymPy 层捕获了全部 6 个等价性错误，Lean 层在覆盖弃权之前就拒绝了全部 2 个证明占位符。这个结果证明验证器是真实的、失效闭合的——它们确实在做逻辑检查，而不是假装在做。

需要强调的是，这是工具证据（instrument evidence），不是模型能力声明。它证明的是"当逻辑错误存在时，验证器能检测到它"，而不是"模型在有验证器时犯更少的错误"。后者需要完整的确认性实验来验证。

### 4.2 主要风险与失败路径

我预判了几个主要风险。第一个风险是验证器太严格——它可能误判正确答案为错误（假阳性）。定位方式是对已知正确的答案运行验证器，测量假阳性率。调整方式是放宽容差（例如 SI 检查的 1% 容差放宽到 2%）。

第二个风险是验证器太宽松——它可能漏判某些类型的逻辑错误（假阴性）。定位方式是使用已植入错误集测量漏判率。调整方式是收紧规则或添加新的检查类别。

第三个风险是覆盖范围太低——太多步骤被弃权，系统几乎没有用。这种情况下的立场是：覆盖低但诚实。一个诚实的弃权优于一个不诚实的放行。随着人类批准的新检查器增加，覆盖范围会逐步扩大。

第四个风险是推理链不忠实——模型 stated 的 chain-of-thought 可能不反映其真实推理过程。定位方式是因果探测：扰动 CoT 的某一步，测量输出是否改变（flip-rate）。高 flip-rate 表示 CoT 是 load-bearing 的；低 flip-rate 表示它是事后合理化。调整方式是仅将 CoT 视为待检查的输入，而非 ground truth。

第五个风险是 LLM 提议的检查器本身有缺陷。定位方式是人类审批加独立专家 AI 审查加可执行测试（正例、反例、畸形输入、安全、回滚）。如果提议未通过任何一关，就保持弃权。

### 4.3 复现与开源计划

这个项目的数据来源是公开的。任务包包含 150 个公开开发任务（物理 50、符号数学 50、Lean 50），覆盖可执行闭题、留出可执行题和前沿缺口题。已植入错误集是 16 个确定性生成的逻辑错误，全部内嵌在包中。此外还有一个独立的归因验证模块，使用公开的哲学语料库（31 条归因记录、219 条已知错误归因、100 条真实归因）。

依赖工具很少。核心验证仅需 Python 3.12 标准库。可选的符号验证层需要 SymPy。PDF 生成需要 pypdf 和 reportlab。不需要 GPU 即可验证核心证据——逻辑错误捕获率审计在普通 CPU 上运行时间不到 1 秒。

运行流程是确定性的。执行 `run_all.sh` 会运行全部确定性测试（超过 200 个），包括环境测试、v2 协议测试、Stage A 校验、逻辑错误捕获率审计、收据协议基准测试和确定性 ZIP 构建验证。执行 `python3 v2/build_logic_error_audit.py --check` 可以单独验证逻辑错误捕获率。执行 `verify_bundle.py` 验证确定性 ZIP 的完整性和声明边界。

复现方式是全 CPU 确定性的。两次连续构建的 ZIP 字节相同。每个公开 JSON 文件都强制携带声明边界（`candidateOnly:true`，`canClaimAGI:false`）。内容寻址的 receipt DAG 可以被任何第三方审计。

开源计划采用 Apache-2.0 许可证。公开代码仓库位于 github.com/tomyimkc/verification-frontier，包含双语（中文和英文）文档。公开 Demo 位于 Hugging Face Space，是一个免登录的 Gradio 应用，零网络调用、零模型调用。初赛后计划继续开发 TUI 集成——将逻辑错误验证器接入 Sophia TUI harness，实现实时步骤级验证和 OKF 进度日志。
